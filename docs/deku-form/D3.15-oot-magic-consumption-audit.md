# D3.15 — OoT magic-consumption integration audit

## Status

**Audit complete; runtime implementation intentionally held.** The Deku bubble currently charges and spawns, but it does not yet consume magic. Do not describe the cost as implemented.

## Verified in the current OoTMM fork

- `packages/generator/include/combo/magic.h` declares:
  - `Magic_RequestChange(PlayState* play, s16 amount, s16 type)`
  - `Magic_RequestChangeCustom(PlayState* play, s16 amount, s16 type)`
  - `Magic_Reset`, `Magic_Update`, and `Magic_Refill`.
- The header defines OoT-specific request types, including `MAGIC_CONSUME_NOW`, `MAGIC_CONSUME_WAIT_NO_PREVIEW`, and `MAGIC_CONSUME_NOW_ALT`.
- The declaration alone does not establish that either request function is linkable from this OoT actor overlay, nor does it establish the correct runtime entry point/ABI. D3.9 already demonstrated why an unverified direct call is unsafe.
- `InterfaceContext` exposes `lensMagicConsumptionTimer` at offset `0x230`, but this is the Lens timer, not a general-purpose magic balance or safe substitute for the engine's magic request routine.
- The current Deku bubble actor has a charge parameter capped at 30, a timer, a collider, and temporary draw geometry. It currently does not call a magic routine.

## Asset finding for the next bubble-rendering increment

The MM and OoT setup definitions both expose an `object_bubble` object with:
- `gBubbleTex` at offset `0x0000` (IA8, 64×64)
- `gBubbleDL` at offset `0x1000`

The Deku bubble actor still draws a temporary `gameplay_keep` display list. The existence of the object definition is confirmed, but its runtime object-slot loading, generated symbol address, and compatibility with the desired Deku projectile appearance still need to be verified before switching the actor to it.

## Required implementation gate

Before adding a magic charge:
1. Identify the actual OoT implementation or stable overlay entry point for `Magic_RequestChange` in the exact OoT build used by this fork.
2. Confirm its calling convention, address/relocation method, and return semantics from a real call site or verified symbol map.
3. Confirm the magic amount representation and whether the function rejects insufficient magic without partially changing state.
4. Define a small, explicit cost policy for Deku bubble firing, including whether charge strength changes cost.
5. Spend magic only after validating the player can fire and only when the projectile spawn succeeds; on insufficient magic, do not spawn and provide a clear failure response.

## Safety decision

No guessed overlay address, direct unverified function call, or manual write to magic state is introduced in this increment. The next code change must be based on verified OoT runtime behavior, then pass the fork's C/TypeScript CI. CI success will still not count as a ROM build or an in-game test.
